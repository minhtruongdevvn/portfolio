🛡️ Dead Sync Handling via Queue-Gated Journaling

Core Philosophy

Instead of traditional DLQs which can obscure ordering, we use a single strict-ordering queue as a temporary journal and gatekeeper. The queue itself is the source of truth for whether the system is in recovery mode.

Key Invariant

Queue Non-Empty ⟹ Dead Sync Mode

The presence of messages in the queue dictates the system state: queue sync and direct sync.

Message Taxonomy

Type Purpose Queue Behavior
failed Source event that failed to sync. Initiates recovery. ✅ Always Accepted
journal Normal sync during recovery. Preserves ordering. ✅ Accepted if Queue Non-Empty
❌ Rejected (400) if Empty

🔹 Operation

  • 1. Syncer attempts direct sync to Elastic.
  • 2. If failed, send email notification and syncer will sync via queue.
  • 3. When the sync error is resolved, system will continue to sync via queue to maintain data integrity until the queue is drained.
  • 4. If a journal message is attempted on an empty queue, it is rejected (400), signaling the client to proceed with direct sync.

🔸 Advantages

  • 1. Zero idle cost: Using Lambda ensures no infrastructure cost when the system is healthy and no dead-sync items exist.
  • 2. Restart safe: The system automatically resumes the correct mode after restarts by checking queue state.
  • 3. Explicit flow control: Synchronous 200/400 responses clearly signal clients whether to enqueue or perform direct sync.
  • 4. Strict ordering during failure: All failed and subsequent operations are processed in a single strict order during recovery.
  • 5. Source-of-truth durability: Failed messages are always accepted, preventing data loss during outages.
  • 6. Minimal normal-path overhead: The queue is bypassed entirely when the system is healthy, keeping latency low.
